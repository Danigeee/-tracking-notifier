# ADR-001: Outbox transaccional en PostgreSQL con un worker propio

- **Estado:** aceptada
- **Fecha:** 2026-10-24

## Contexto

El servicio recibe cambios de estado de guías y debe avisar al sistema de cada cliente mediante un webhook. El enunciado impone tres exigencias que chocan entre sí:

1. **No perder eventos.** Si un cliente se entera de menos eventos de los que ocurrieron, el servicio no cumple su propósito.
2. **El envío no puede bloquear la respuesta** al sistema que registra el evento.
3. **El webhook del cliente es poco fiable:** puede estar caído, lento o devolver errores. Hay que reintentar con espera creciente, hasta 5 intentos, y dejar consultables los avisos que fallen.

La dificultad de fondo es que cada evento exige **dos cosas que deben ocurrir juntas**: guardarlo en la base de datos y dejar constancia de que hay que avisar. Si se hacen por separado, un fallo entre ambas deja el sistema inconsistente: un evento aceptado sin aviso (se pierde) o un aviso de un evento que no se guardó.

## Decisión

Usar el patrón **outbox transaccional** sobre la misma base PostgreSQL, con un **worker propio** que entrega los avisos:

1. Al registrar un evento, **en una sola transacción** se guardan la guía, el evento y una fila en la tabla `notificaciones` con estado `PENDIENTE`. Si algo falla, no queda nada de las tres. La API responde de inmediato, sin esperar al cliente.
2. Un **worker** dentro del servicio revisa cada pocos segundos las notificaciones que ya toca enviar, las **reclama** de forma exclusiva y las entrega con `POST`, con timeout de 5 s y firma HMAC.
3. El resultado se guarda: `ENVIADA`; o `PENDIENTE` con el `proximo_intento` calculado (10 s, 1 min, 5 min, 30 min); o `FALLIDA` tras el quinto intento, consultable por la API.

Dos detalles de implementación hacen que esto sea correcto con varias instancias:

- **Reclamo atómico.** Una sola sentencia `UPDATE ... WHERE ... IN (SELECT ... FOR UPDATE SKIP LOCKED)` elige un lote y lo **reserva** por 60 s moviendo su `proximo_intento`. Dos instancias nunca toman el mismo aviso; y si una muere a mitad, la reserva vence y el aviso se retoma sola, sin perderse.
- **Los avisos de un cliente sin webhook no se reclaman.** Se filtra dentro de la propia subconsulta, no después: así no ocupan el límite del lote ni bloquean a los demás clientes. Quedan `PENDIENTE` sin gastar intentos y salen en cuanto el cliente configure su URL.

En el código, la transacción es un puerto (`UnidadDeTrabajo`) del que dependen los casos de uso, de modo que el dominio y la aplicación no conocen PostgreSQL. La atomicidad se comprueba en las pruebas de integración contra una base real.

## Alternativas consideradas

### A. Llamar al webhook dentro de la petición
Es lo más simple, pero incumple las tres exigencias: el envío bloquearía la petición (la respuesta tardaría hasta lo que tarde el cliente), no habría dónde guardar el aviso para reintentarlo ni para consultarlo después, y si el webhook falla o el servicio se cae a mitad, el aviso se pierde sin dejar rastro. **Descartada.**

### B. Enviar "en segundo plano" desde memoria (`setImmediate`, promesa sin esperar, cola en memoria)
Responde rápido, pero los avisos pendientes viven solo en la memoria del proceso: un reinicio o una caída los pierde, y tampoco quedaría un registro consultable de los que fallen. Incumple la exigencia de no perder eventos. **Descartada.**

### C. Broker externo (RabbitMQ, SQS, Kafka)
Resuelve la cola y los reintentos, pero reintroduce el problema de fondo: hay que **escribir en dos sistemas** (la base y el broker) sin una transacción que los cubra. Si se publica antes de confirmar la base, se avisa de un evento que no existe; si se publica después, un fallo entre ambos pierde el aviso. La solución estándar a ese problema es… un outbox en la base. Es decir, el broker no elimina esta decisión y además suma infraestructura que operar, asegurar y probar. **Descartada para este alcance**, pero compatible: más adelante el worker podría publicar al broker en lugar de llamar a los webhooks.

### D. Captura de cambios de la base (CDC, por ejemplo Debezium)
Evita el sondeo, pero exige infraestructura pesada (Kafka, conectores) desproporcionada para este servicio. **Descartada.**

## Consecuencias

**Positivas**
- **Garantía fuerte contra pérdida:** un evento aceptado siempre tiene su aviso registrado, y el aviso no se descarta hasta que el cliente confirma o se agotan los intentos.
- **Una sola pieza de infraestructura** (PostgreSQL): menos que operar, y las pruebas de integración cubren el comportamiento real.
- **Estado observable:** el estado de cada aviso, los intentos y el último error están en una tabla y se consultan por la API (`GET /notificaciones?estado=FALLIDA`).
- **Escala horizontal del envío** sin coordinación extra, gracias al reclamo con `SKIP LOCKED`.

**Negativas y riesgos aceptados**
- **Entrega "al menos una vez", no "exactamente una":** si el servicio se cae después de entregar y antes de guardar el resultado, el aviso se reenvía. Se mitiga con la cabecera `X-Event-Id` (igual en todos los reintentos) para que el cliente deduplique. No se puede evitar del todo con un receptor externo.
- **Sin garantía de orden entre avisos** de una misma guía: se envían en paralelo y cada uno tiene sus propios reintentos. El cliente puede ordenar por `fechaEvento`. Garantizar el orden exigiría serializar el envío por guía, con costo en latencia.
- **Latencia de entrega:** hasta el intervalo del worker (2 s por defecto) más el tiempo de envío. Es "casi en tiempo real", no inmediata. Se puede bajar con `WORKER_INTERVAL_MS`, a costa de más consultas.
- **La base de datos es el límite:** el sondeo y las escrituras de resultado cargan a PostgreSQL. Con mucho volumen habría que particionar o archivar la tabla `notificaciones` y valorar el cambio a un broker (alternativa C).
- **Reservas de 60 s:** si un envío tardara más que eso, otra instancia podría tomar el mismo aviso. El timeout de 5 s deja un margen amplio.

## Cómo se verifica

Las pruebas de integración (`npm run test:integration`) demuestran esta decisión contra PostgreSQL real:

- Si algo falla tras guardar la guía y el aviso, **no queda nada**; y si falla el aviso, el evento tampoco queda.
- 10 peticiones simultáneas con el mismo `eventId` dejan 1 evento y 1 aviso.
- 3 instancias del worker trabajando a la vez entregan cada aviso **exactamente una vez**.
- Una reserva vencida devuelve el aviso a la cola; una vigente impide que otro lo tome.
- 30 avisos antiguos de un cliente sin webhook **no impiden** enviar los de otro.

Para comprobar que estas pruebas detectan fallos, se rompió el código a propósito (quitar el bloqueo, quitar la reserva) y se verificó que fallan.
